## Функции

| ID | Статус | Что | Заметка |
|----|--------|-----|---------|
| F1 | принято | **Автопроверка обновлений при запуске** | Тихая проверка при наличии сети. **БД** (`manifest.json` / `data_version`) — всегда. **Приложение** (`app-manifest.json` / `version_code`) — только sideload / установка из файла (installer не `ru.vk.store` / `com.android.vending`; канал как у F2). Сигнал ненавязчивый: **одно** сообщение (snackbar/banner), без модалок и без автоустановки. В меню оба пункта: если обновление уже известно — сразу состояние «есть обновление» + действие загрузить (как сейчас после ручной проверки), а не снова «Проверить…». Без сети / ошибка — молча. |
| F2 | сделано | **Обновление приложения для non-store установок** | UI в «О приложении»: проверка только если installer не из стора (`ru.vk.store`, `com.android.vending`). Канал: `mobile-pack/app-manifest.json` (`publish_downloads.sh` вместе с APK) + `/app/apk/`. Сравнение только `version_code`. Тихая проверка на старте — в F1. |
| F3 | принято | **Отчёт об ошибке по согласию** | После необработанной ошибки (и pending при следующем запуске): короткий диалог «Отправить анонимный отчёт?». POST JSON на endpoint в **punzh-dict**. Payload: версии app/data/schema, manufacturer/model/Android, тип/сообщение/stack (обрезанный). Без поисковых строк и PII. Антиспам: клиент — только из диалога, cooldown, один `client_report_id`; сервер — rate limit по IP, max body, схема полей, маркер `X-Punzh-App`. Без SaaS и без автоотправки. |

## Рефакторинг

Из отложенного после v1 (делать **по касанию фичи**, не hygiene ради SOLID).

| ID | Когда трогать | Что | Не делать «просто так» |
|----|---------------|-----|-------------------------|
| R1 | Следующая крупная UX-правка Home | Вынести letter window / n-gram rail из `_HomeScreenState` в обычный контроллер (без BLoC/Riverpod) | Полный rewrite Home «для красоты» |
| R2 | Новая ось поиска / фильтров (напр. RU+tags) | Узкий split search-методов repo или общий `run(query, filters)`; **не** Strategy/SearchBackend заранее | Паттерн Strategy для KRL/RU «на вырост» |
| R3 | Второй backend или тяжёлый widget-тест Home | Abstract `IDictionaryRepository` / DI | Интерфейсы над одним sqlite |
| R4 | Рост SQL/поиска + реальная новая ось | Sibling-классы / private helpers вокруг `DictionaryRepository` | Преждевременная нарезка «толстого» repo |
| R5 | Касание drawer / update UI (в т.ч. F1) | Вынести `_UpdateDbPane` в отдельный файл | — |
| R6 | Второй UI-потребитель preview | `formatPreview` рядом с `article_format` | Перенос `previewLine` без нужды |

**Сознательно раздельно:** `orthography` ≠ `prepareKrlIlikeQuery` (разные порты Django); sheet ≠ route для статьи.
